# Standing grants gate shared actions, read only from the committed default branch

A grant in a Project's `docs/agents/supervision.md` lets `/supervise`'s machinery -- the `deny-shared-actions.sh` hook (#66) and `actions.sh`'s report (#58) -- treat a push, PR or issue action as pre-approved instead of stopping for the maintainer. `docs/agents/supervision.md` holds one `## Grants` section of bullets, `- <action>` or `- <action>: <note>`, where `<action>` is `push`, `distribution-push`, `pr-create`, `pr-merge`, `issue-close`, `issue-comment`, `issue-create`, `sub-issue`, `label` or `checked-push` (`issue-comment` and `issue-create` added by #110, so an unattended capture can post its findings; `distribution-push` by #141, below; `sub-issue` by #162, so it can put a ticket it files under the work's parent; `label` by #184, so it can make the `in-motion` and live-check relabels; `checked-push` by #188, which covers no worker action at all: it lets the supervisor's own Push on approval push without asking when every check passes, ADR 0007). A new script, `skills/supervise/scripts/grant.sh`, is the one place that reads it: given `--dir` and `--action`, it prints the matching bullet (the citation) and exits 0 when granted, or exits 1 with nothing on stdout otherwise.

grant.sh reads the file from `origin/<default>` as committed -- `git show origin/main:docs/agents/supervision.md`, say -- never DIR's working tree, index, or local branch tip. A `/supervise` worker commits directly on the default branch in DIR (ADR 0003: there is no per-ticket feature branch), so the working tree and the local branch tip are exactly what the worker's own commits reach. Reading only the remote-tracking ref means a grant has to be pushed before it counts, and `deny-shared-actions.sh` already refuses a worker's own push (#66) unless a grant already covers it -- so a worker cannot grant itself one by committing and pushing a new line. When grant.sh finds no match on the committed ref but finds one on the working tree or local branch, it still refuses, and notes the ignored grant on stderr, so a mistaken or tampered local edit is visible rather than silently inert.

`deny-shared-actions.sh` maps the handful of forms its scan already names exactly (`git push`, `git subtree push`, `git send-pack`, `gh pr create`, `gh pr merge`, `gh issue close`, `gh issue comment`, `gh issue create`, and a `gh issue edit` that only adds or removes labels) to an action and asks grant.sh before refusing; granted, it lets the command through unchanged -- the worker's own push goes ahead, not a substitute performed later by the supervisor. The piped-into-a-shell fallback and the gh api forms are never granted, since a grant names an action the scan told apart from the others, and those were not; the exceptions are a gh api POST to an issue's comments or to a repo's issues, which the scan names as the issue comment or new issue it makes (#110), and a gh api POST to an issue's `sub_issues` or PATCH to its `sub_issues/priority`, which the scan names as the sub-issue link or reorder it makes, for the `sub-issue` grant (#162). That grant covers linking and reordering only: removing a sub-issue (a DELETE), a PATCH of the issue itself, and any other method on those paths stay refused under it. The grant's note says which tickets it covers, as `issue-create`'s does (a capture's tickets, under the work's own parent, and for a worker that parks its ticket, its own ticket to the end of its parent's order, #158); the hook enforces the action, not which ticket it moves. The `label` grant covers `gh issue edit` with only `--add-label` or `--remove-label` (#184). An edit that also sets another field (`--title`, `--body`, an assignee) is named apart and no grant covers it; the hook reads the other fields in the edit's own words, the command split at separators outside quotes, so a quoted `;` in a label cannot hide a title. A label write through gh api (a POST, PUT or DELETE on an issue's labels, or a GraphQL `addLabelsToLabelable`) stays refused under every grant, and the note, not the hook, says which labels the grant is for. `issue-comment` covers posting a new comment only: `gh issue comment --edit-last` and `--delete-last`, and a gh api PATCH or DELETE of a comment, are named apart and no grant covers them (#113); no separate action grants editing or deleting, since a worker's findings need only new comments. `issue-create` covers `gh issue create` and the gh api POST to a repo's issues. A GraphQL mutation stays refused under every grant, `addComment`, `createIssue` and `addSubIssue` included: one document can carry several mutations under aliases, its text can come from a file or variables the scan does not read, and `addComment` also comments on pull requests, so naming one from its text would grant more than the action says (#113). `actions.sh` asks the same question to cite a grant on a branch or command line (`granted (<citation>)` instead of `ungranted`), using a looser, text-based guess at the action (`action_for`) good enough to cite, not to enforce -- enforcement stays in the hook. Because `actions.sh` also uses the hook as a probe to decide whether a past command is worth listing at all, that probe sets `MP_DENY_SHARED_ACTIONS_IGNORE_GRANTS=1` so a grant added after the fact cannot make a command that was actually refused at the time drop out of the report; the variable can only make the hook refuse more, never less. grant.sh's own note of a grant it found only on the working tree or an unpushed commit is surfaced in `actions.sh`'s report as a `note` line, not swallowed, so a tampered or merely premature grant is reported rather than quietly treated as absent -- the first comment's "a grant added on the ticket branch is ignored and reported" reaches the report this way, not only grant.sh's own stderr. `grant_label`, the function that decides this, is called directly rather than through a command substitution, because `note()` mutates a shared accumulator and that mutation would be lost if it ran inside a subshell.

A grant names an action, and until #141 not a repo: `push` covered a push wherever the worker ran it, and the git wrapper read the grant from the repo the push acted on. A Project whose code lives in a separate Distribution repo (#125) is often a private `-dev` tracker beside a public repo, so a `push` granted for the tracker would also have let the worker publish the public one, under whatever that repo's own `supervision.md` said. So a push in a Project's Distribution repo is its own action, `distribution-push`, granted only by the Project's `supervision.md`; `push` covers only the Project's own repo, and the Distribution repo's own grants are not read for it. The classifier the hook and the wrappers share (`classify_distribution`) names such a push `git push in Distribution repo <path>` and moves the grant lookup to the Project. It finds the Project from the Distribution repo's worker marker (`project <path>`, written by `launch.sh`) or the session's own folder, and accepts it only when `distribution.sh`, reading the Project's origin, names that repo: a marker a worker rewrote can point the lookup elsewhere, but cannot make an unrelated repo a Distribution repo. A push found in no Project this way reads the repo's own grants, as before: a worker that removed the marker and ran its push from inside the Distribution repo would reach that repo's own `supervision.md`, which grants nothing unless that repo has one. The hook also follows a `cd <dir>` before the git, so `cd <repo> && git push` reads that repo's grant, not the session folder's. Without the grant the push waits, and `push.sh` checks and pushes both repos on one approval (ADR 0007).

The `issue-close` grant covers the worker's own ticket after its work is pushed, and with a gated Distribution push that work can still be local when the worker reaches the close (#186). So the hook and the wrappers hold the close: after `grant.sh` grants `issue-close`, `classify_close_held` refuses it while a Distribution repo of the Project, found as `classify_distribution` finds it, holds commits its upstream lacks or has no upstream. The worker lists the close with its push (`Waiting on: git -C <dist> push origin <branch>; gh issue close <N>`), and `capturing`'s `before-clear.sh` reports the held close as `ungranted`. The supervisor's `close.sh` settles it after the maintainer answers the push: `--pushed` closes the ticket under the grant, or the maintainer's own yes, once the Distribution repo is even with its upstream, and records the close so `actions.sh` names it as the supervisor's; `--declined` keeps the ticket open, relabelled `ready-for-human` with a comment naming the unpushed commits. Reopening the ticket only on a declined push was considered and rejected: the tracker would read done for the whole wait, and a supervisor session that ended before the maintainer answered would leave it closed with nothing landed.

A worker could still make a grant meaningless a different way: editing `docs/agents/supervision.md` itself, or the profile directory's rules, settings and hooks that gate it, ahead of a future commit. `deny-worker-grant-edits.sh`, a new PreToolUse hook gated the same way as `deny-shared-actions.sh` (unattended and auto mode), refuses an Edit, Write or NotebookEdit targeting the grant file in the checkout, or any path under `$CLAUDE_CONFIG_DIR` other than the session's own job folder (`$CLAUDE_CONFIG_DIR/jobs/<first 8 characters of the session id>`, where Claude Code tells a background session to keep its temp files; #112, #173), compared after `..` and symlinks are resolved. It first left a file written from Bash uncovered, as `supervise-read-only.sh` still does on the attended side of this checkout; a worker then rewrote a profile rule by writing a Python script into its job folder and running it from `<profile>/rules`, and the gate scripts themselves sit in the plugin cache under the profile directory. So from #173 the hook also reads a Bash command's text, quotes and heredocs parsed, and refuses a write it can see to a protected path: `>`, `>>` and `&>` redirection, `tee`, `sed`/`perl`/`ruby -i`, `cp`, `ln` and `install` onto one, `mv`, `rm`, `touch` and the like on one, `dd of=`, and the same inside `sh -c`, `eval` and a process substitution, with `$CLAUDE_CONFIG_DIR`, `$CLAUDE_JOB_DIR`, `$HOME` and `~` expanded (a `${VAR:-default}` form included) and every `cd` and `pushd` followed. It also refuses an interpreter, a sourced script, an awk program that can write, or a script run while the working directory, after any `cd`, is in the profile directory outside the job folder. Reads and `claude plugin update` are not refused. A text scan stays incomplete by nature: a path built at run time, a program that writes on its own (`python3 -c` with an absolute path), `find -exec`, `xargs`, `rsync`, `patch` and `git checkout` get through, and the supervisor's after-run comparison of the protected files reports them instead (#190).

## Considered Options

- **A separate script the worker calls to request a shared action.** Rejected: `/implement` and the rest of the build loop know nothing about grants, so a worker would have to be taught to call it instead of running `git push` as normal, and nothing in this ticket changes the worker's own skills. Folding the grant check into `deny-shared-actions.sh`'s existing scan needs no such change: the worker's commands look exactly as they always have, and the hook decides.
- **The supervisor performs the granted action itself, after the fact.** Considered for "the same push goes ahead" (the acceptance criterion's own words), then rejected in favor of letting the hook allow the worker's own attempt through: a substitute push performed later by the supervisor is a different push, with its own branch and timing questions ADR 0003 already treats as the supervisor's to stay out of (it holds the checkout read-only while a worker runs). Letting the hook decide needs nothing from the supervisor at all.
- **Read the grant file from the working tree, with a warning.** Rejected: a warning a human might not read before the action already ran is not a gate. Reading only the committed, pushed, default-branch ref is what makes the hook's own refusal of a worker's push (#66) load-bearing for the grant's integrity, not just incidental.

## Consequences

- `tests/grant.test.sh` covers grant.sh directly: a bare and a noted grant, an unmatched action, a decoy bullet outside the `## Grants` section, a grant on the working tree or an unpushed local commit (ignored, noted), and no origin remote at all (ungranted, no crash).
- `tests/deny-shared-actions.test.sh` adds a scratch repo with a committed, pushed grant: a granted push and a granted `gh issue close` go through; an ungranted action in the same checkout, and a `gh api` form alongside a push grant, still refuse; a grant only in the working tree still refuses.
- `tests/supervise.test.sh` adds a granted-push case to `actions.sh`'s report (citing the grant on both the branch and the command lines, including one the hook itself refused at the time), an unmatched-grant case (the push line stays `ungranted`), and a working-tree-only grant case (reported as a `note` line, not silently absent). Its own `MP_DENY_SHARED_ACTIONS_IGNORE_GRANTS` prefix needed no new test-hygiene fix, since `refused()` always sets it explicitly rather than reading it from the ambient environment; `tests/deny-shared-actions.test.sh`, which invokes the hook directly, now unsets it for the same reason the file already unsets the `git config`-related variables.
- `tests/deny-worker-grant-edits.test.sh` covers the new hook: the grant file in a checkout, a relative path, a nested cwd, a sibling file that is not the grant file, the profile directory and a path that only shares its prefix, an unattended session outside auto mode, and the maintainer's own attended session. From #173 it also replays the shape that rewrote a profile rule (a heredoc into the job folder allowed, the script run from `<profile>/rules` refused), runs each Bash write form against the grant file, `distribution-repo.md`, a profile rule and another job's folder (refused) and against a sibling file and the session's own job folder (allowed), and checks `..` and symlink escapes from the job folder, reads of protected paths and a plugin update (allowed).
- `deny-shared-actions.sh` inspects only the command text Claude Code hands it, never what a named script goes on to run. ADR 0006's git and gh wrappers, on a background session's PATH, ask grant.sh the same question about the arguments a script's git or gh actually runs with.
- `setup-mp-ported-skills`'s `scripts/setup.sh` gains a `--project-dir` option and a `supervision-doc` feature (report-only state, `write` instead of on/off) that scaffolds an empty `docs/agents/supervision.md` in a Project, explaining the format and that an empty file grants nothing. It is not a profile setting, so it reads and writes outside `$CLAUDE_CONFIG_DIR`, as the later `distribution-repo` feature (#143) does for `docs/agents/distribution-repo.md`.
- `watch.sh` gains a `hang` state and a `--stall` option (default 1800s): a worker whose transcript has not grown in that long is reported as a hang and left running, distinct from the outer `--timeout`'s hard stop. A long tool call can hold the transcript's size steady in its own right (Claude Code appends the result only once the call returns), so `hang` is a "no progress for a while" signal to report, not proof the worker is stuck.
