# The shared-action deny hook gates on unattended plus auto mode, not on a profile-wide deny

A background worker (`claude --bg`, as `/supervise` launches per ADR 0003) runs in the same profile as the maintainer's own interactive sessions, so nothing in the profile's settings tells a `git push` one of them runs from a `git push` the other runs. `plugins/mp-ported-skills/hooks/hooks.json` registers a PreToolUse hook, `scripts/deny-shared-actions.sh`, matched on the `Bash` tool, that refuses `git push`, `gh pr create`, `gh pr merge`, `gh issue close`, and a `gh api` write that reaches the same actions, only when both hold: `CLAUDE_CODE_SESSION_ATTENDED=0` in the hook's own process environment, and the PreToolUse payload's `permission_mode` field reads `auto`. Either alone is not enough: an unattended session outside auto mode already blocks on its first ordinary permission prompt, and an attended session in auto mode is the maintainer's own.

## Considered Options

- **A profile-wide `deny` rule, e.g. `Bash(git push*)`.** Rejected twice over: a prefix rule misses `git -C . push` and other equivalent forms a PreToolUse hook that parses the command catches instead; and the supervisor runs in the same profile as its workers, so a deny in `settings.json` would block the supervisor's own push too, standing grant or not.
- **Tag each worker with a launch-time environment variable.** Rejected: the background daemon pre-spawns spare hosts before a launch's arguments are known, so a variable set at `claude --bg` time may never reach the process that ends up running the worker (confirmed against `launch.sh`, which instead reads the job's `state.json` after the fact to check what a worker actually got).
- **Tag each worker via a launch flag.** Rejected on the same ground as ADR 0003's follow-up problem: a `--resume` that passes any flag, or that targets a still-live session, starts a copy under a new id, so a flag set at the original launch does not reliably describe the session a later hook run inspects.

## Consequences

- `CLAUDE_CODE_SESSION_ATTENDED` is not documented by Claude Code; it was found by reading `env` inside a live `claude --bg` session (CLI 2.1.284) alongside that job's `state.json`, which confirmed the session was launched in auto mode via `--permission-mode auto`. The hook reads its absence as attended, so this backstop goes quiet, not tight, if a future CLI release stops setting it -- the auto-mode classifier is still the deciding layer underneath it. `tests/live/deny-shared-actions.sh` checks that a hook in a real background session sees the variable and refuses `git push --dry-run`.
- The variable is fixed when the session's process spawns, so `claude attach` to a worker keeps the gate: the maintainer cannot push from inside an attached worker while it stays in auto mode. That is intended, since the process cannot tell who is typing. The hook reads `permission_mode` on every call, so switching the attached session out of auto mode should lift it (not yet checked live); otherwise push from the maintainer's own interactive session.
- `permission_mode` in the PreToolUse payload is documented (https://code.claude.com/docs/en/hooks.md); nothing else about background-session detection is.
- The command scan splits on separators, parens and backticks, drops quotes and backslashes, matches the program by basename, and skips the words that run what follows them: `VAR=value`, shell keywords, `env`, `command`, `builtin`, `exec`, `time`, `nohup`, `nice`, `timeout`, `xargs`, `eval`, and `sh -c` or a here-string with its sibling shells; when the command pipes into a shell, it checks the whole command for the words of a refused form. It treats `git send-pack` and `git subtree push` as pushes, resolves a git alias defined with `-c alias.X=...` or in git config, and refuses a `gh api` call that writes (any method but GET, and POST by default once a field is given) to pulls, issues, merges, contents or the git data API, and any GraphQL mutation in the command text. Known gaps: a command built from variables (`g=git; $g push`), a wrapper it does not list (`sudo`, `find -exec`), and a GraphQL mutation read from a file. It does not parse quoting, so a separator inside a quoted string splits too, and `git commit -m "a; git push"` is refused. That trade is deliberate: in an unattended session a false refusal costs a detour through the supervisor, and a miss publishes.
- #66's third criterion, that #58's grant check is the only route to a shared action, waits on #58. The hook inspects only the command text Claude Code hands it, never what a named script goes on to run, so any script that pushes is a route around it today. When #58 names its grant script, the hook can narrow to it; until then `tests/deny-shared-actions.test.sh` pins the script route as open under a name that says it waits on #58.
