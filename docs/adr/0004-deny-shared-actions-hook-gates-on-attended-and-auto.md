# The shared-action deny hook gates on unattended plus auto mode, not on a profile-wide deny

A background worker (`claude --bg`, as `/supervise` launches per ADR 0003) runs in the same profile as the maintainer's own interactive sessions, so nothing in the profile's settings tells a `git push` one of them runs from a `git push` the other runs. `plugins/mp-ported-skills/hooks/hooks.json` registers a PreToolUse hook, `scripts/deny-shared-actions.sh`, matched on the `Bash` tool, that refuses `git push` (including `git -C <dir> push` and one inside a compound command), `gh pr create`, `gh pr merge` and `gh issue close` only when both hold: `CLAUDE_CODE_SESSION_ATTENDED=0` in the hook's own process environment, and the PreToolUse payload's `permission_mode` field reads `auto`. Either alone is not enough: an unattended session outside auto mode already blocks on its first ordinary permission prompt, and an attended session in auto mode is the maintainer's own.

## Considered Options

- **A profile-wide `deny` rule, e.g. `Bash(git push*)`.** Rejected twice over: a prefix rule misses `git -C . push` and other equivalent forms a PreToolUse hook that parses the command catches instead; and the supervisor runs in the same profile as its workers, so a deny in `settings.json` would block the supervisor's own push too, standing grant or not.
- **Tag each worker with a launch-time environment variable.** Rejected: the background daemon pre-spawns spare hosts before a launch's arguments are known, so a variable set at `claude --bg` time may never reach the process that ends up running the worker (confirmed against `launch.sh`, which instead reads the job's `state.json` after the fact to check what a worker actually got).
- **Tag each worker via a launch flag.** Rejected on the same ground as ADR 0003's follow-up problem: a `--resume` that passes any flag, or that targets a still-live session, starts a copy under a new id, so a flag set at the original launch does not reliably describe the session a later hook run inspects.

## Consequences

- `CLAUDE_CODE_SESSION_ATTENDED` is not documented by Claude Code; it was found by reading `env` inside a live `claude --bg` session (2026-09-29, CLI 2.1.284) alongside that job's `state.json`, which confirmed the session was launched in auto mode via `--permission-mode auto`. The hook reads its absence as attended, so this backstop goes quiet, not tight, if a future CLI release stops setting it -- the auto-mode classifier is still the deciding layer underneath it.
- A script the supervisor runs to perform a grant under #58 is a different Bash command from `git push` itself, so the hook does not need to special-case it: it only ever inspects the literal command text Claude Code hands it, never what a named script goes on to run.
- `permission_mode` in the PreToolUse payload is documented (https://code.claude.com/docs/en/hooks.md); nothing else about background-session detection is.
- The command scan sees through a leading `VAR=value` assignment and a leading `env` (`env FOO=bar git push`, `FOO=bar git push`), since those are plain unquoted words the line-and-word splitter tokenizes correctly. It does not follow `sh -c '...'`, `eval '...'`, or any other interpreter indirection: making that reliable needs the one quoted argument that carries the nested command told apart from several unquoted words, and this splitter does not parse shell quoting -- a partial attempt at it either cuts a quoted `git push` in two (missing the real thing) or fires on a quoted string that only mentions `git push` in prose (a false deny on unrelated work). `tests/deny-shared-actions.test.sh` pins `sh -c "git push"` as passing through uncaught, so the gap reads as a deliberate boundary rather than an unnoticed regression.
