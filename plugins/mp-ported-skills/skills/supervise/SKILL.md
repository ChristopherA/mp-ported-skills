---
name: supervise
description: Run a Project's next ready-for-agent ticket, or with --loop each next one in turn (--loop N for at most N), through the full /implement in a Claude Code background session, and report done or blocked.
disable-model-invocation: true
---

Run one ticket in a Project, from the Hub or from inside the Project, as the maintainer would by hand: read the next step, start `/implement #N` in a fresh session, watch it, and report. The worker is a Claude Code background session (`claude --bg`), whose first prompt enters through the human's door, so the ticket gets the full `/mattpocock-skills:implement`, its TDD and its own `/code-review` (ADR 0003). One ticket, then stop; with `--loop`, the next ticket after each one that lands, until a rule stops it, and with `--loop N`, at most N tickets (Loop, `loop.md`).

The Project folder, relative to this session's folder or absolute, is the first word here (`.` when this session runs inside the Project); `--model <id>`, `--effort <level>`, `--watch tmux` or `--watch iterm`, and `--loop`, optionally with a ticket count (`--loop 2`), may follow: $ARGUMENTS

## Policy

The supervisor drives build-loop defaults and nothing else:

- **It may**: take the step `state.sh` names, launch `/implement #N` for a `ready-for-agent` ticket, watch the worker, send it a build-loop follow-up (Follow-ups, below), answer a routine question its policy already decides (Routine answers, `routine-answers.md`), capture a worker whose zone reading passes its threshold and continue its ticket in a fresh worker (Zone capture, `zone-capture.md`), and stop a worker that finished or failed a launch check.
- **It stops for anything that changes the spec**: any other step, any other question the worker asks, a permission prompt, a ticket that needs a decision. It reports these and answers none of them. The human answers in the worker with `claude attach <id>`, or in the approval request the Claude app shows for the worker's permission prompt.
- **Shared actions are gated on standing grants, never on the worker's own say.** A push, PR, issue close, issue comment or new issue that `/implement` or a capture reaches is refused by a PreToolUse hook (#66) unless a grant in the Project's `docs/agents/supervision.md` covers it, read only from the default branch as committed on origin -- never the worker's working tree or local commits, which a worker can reach without the maintainer seeing it, and never the worker's to add (#58, docs/adr/0005). With no such file, or no matching grant, the push stops for approval exactly as before; in a background session the `git` and `gh` wrappers below refuse it outright, in any permission mode. `launch.sh` tells the worker, in an `--append-system-prompt`, which shared actions its Project grants, from the same source through `grant.sh`, that a granted one goes ahead without asking, and that any other ends its turn on one line, `Waiting on: <action>`, without trying it (#88): without that, a worker asks before every push and the run stalls at `blocked` with a grant in place. With one, the worker's own attempt goes through, and `actions.sh`'s report (step 4) cites the grant on that line instead of marking it `ungranted`; the report still lists every shared action the worker took, granted or not, in case a form got past the hook or an older worker predates it. A second hook (`deny-worker-grant-edits.sh`) refuses a worker's own Edit, Write or NotebookEdit, or a Bash write it can read in the command (#173), to that grant file, and to anything under this session's own profile directory but the worker's job folder, so a worker cannot grant itself one or change what gates it. A push from inside a script, which the hook cannot see, meets the same check in the `git` and `gh` wrappers a SessionStart hook puts first on a background session's PATH (docs/adr/0006). A push no grant covers, which the worker ends its turn waiting on, is the supervisor's to make, and only on the maintainer's go-ahead given in this session, after checking it (Push on approval, `push-on-approval.md`; docs/adr/0007). So is an issue comment or new issue no grant covers that the worker's capture lists, whether the capture ends on `Waiting on:` or on a statement, under the same terms (Post on approval, `post-on-approval.md`). The supervisor's push has one exception, a `checked-push` grant (#188): under it, the supervisor pushes without asking when every check passes, the suite's included, and no README, CHANGELOG, `docs/` or `.md` file changed, and asks otherwise. It never covers a worker's own push, which the hook and the wrappers still refuse. A message typed into the worker is not a grant, and the hook refuses the worker's push after one.
- **The supervisor stays read-only in the Project while a worker runs**, whether it runs from a parent folder or inside the Project, where the two share one working tree. No file edits, and no git `commit`, `merge`, `rebase`, `checkout`, `switch`, `reset` or `stash` there; reads, `gh` and these scripts still run. `launch.sh` marks the checkout with the worker's id, a PreToolUse hook (#76) refuses those calls in any attended session while the mark is there, the maintainer's own included, and `release.sh` clears it in the Report step. A refusal names the worker and `claude attach <id>`.
- **A worker stays in the Project folder, on its branch, for the whole run**: its commits would otherwise land on a branch nobody pushes. It is launched without the `EnterWorktree` tool and with the background service's worktree guard off (`bgIsolation: none`), so its edits in the folder are not refused. It is stopped at launch if the background service placed it elsewhere, and the moment `watch.sh` sees it leave the folder, or sees a worktree or branch made in the Project's repo since the launch.
- **A Project's Distribution repo is held like the Project** (#125). A Project whose code is committed to a separate repo cloned beside it names that repo in `docs/agents/distribution-repo.md`: one path line, relative to the Project repo's top or absolute. The supervisor reads it from the default branch as committed on origin, as it reads grants, never the working tree (`distribution.sh`), when it takes the snapshot and launches, and keeps the path for the run in the snapshot and the worker's markers; a copy present locally but not on origin is ignored, with a `note: ... ignored` line. The worker still runs in the Project folder, so `gh` reads the Project's tracker, and edits and commits in the Distribution repo by path. The launch checks that repo as it checks the Project, writes the worker's marker there too, so this session stays read-only in both, and the watch counts a worktree or branch made there. `deny-worker-grant-edits.sh` refuses a worker's edit to `distribution-repo.md`, as to the grant file. A push in the Distribution repo is its own shared action, `distribution-push` (#141): only a `distribution-push` grant in the Project's `supervision.md` covers it, `push` covers only the Project's own repo, and the Distribution repo's own `supervision.md` is not read for it. The hook, the `git` wrappers, `launch.sh`'s grants text and `actions.sh`'s citation all tell the two repos apart. Without that grant the worker ends on `Waiting on: git -C <repo> push ...`, alone or after the Project's own push; wherever this skill routes a `needs` line that is a `git push` no grant covers, that line counts as one, and Push on approval (`push-on-approval.md`) checks and pushes both repos on one question. Closing the worker's ticket waits for that push (#186): while the Distribution repo holds commits its upstream lacks, the hook and the wrappers refuse the worker's `gh issue close` even under an `issue-close` grant, and the worker lists the close with its push; Push on approval then closes the ticket with `close.sh --pushed` after the push lands, or, when the maintainer declines it, keeps the ticket open as `ready-for-human` with `close.sh --declined`. With no `distribution-repo.md`, nothing here changes.
- **The supervisor runs from the main checkout, never a linked git worktree** (#79). A worker launched in a worktree commits to that worktree's branch, which nobody pushes, and passes the launch's folder checks, since its folder matches the one it was given. A supervisor can be in one without choosing it: a `claude remote-control --spawn worktree` server gives each session started from the Claude app or iOS its own worktree, so `.` resolves there. `step.sh` and `launch.sh` both refuse a Project folder in a linked worktree, naming the worktree, its branch and the main checkout (`main-checkout.sh`); report it and tell the maintainer to run `/supervise` from the main checkout.
- **A worker that stops making progress is reported, not stopped.** `watch.sh --stall` (step 3) reports `hang` when the worker's transcript has not grown in that long, distinct from a permission prompt or a question: the worker is left running, since a long tool call can hold the transcript steady in its own right, so this is a "no progress for a while" signal, not proof of a real hang.

## 1. Step

With `--loop`, read `${CLAUDE_SKILL_DIR}/loop.md` before anything else: it says what to do between tickets, and with `--loop N` it checks the count first, so launch nothing when it is refused.

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/step.sh" "<project folder>" </dev/null
```

It runs `resuming`'s `state.sh` in the folder and reads the `next:` line. `implement #N` means the step is `/implement` of a `ready-for-agent` ticket with nothing else in flight: go on. `continue #N from <sha>` means the only thing in flight is unpushed commits on the default branch that the newest run record on #N accounts for exactly: a supervised run of #N that ended before its work was pushed, such as one whose supervisor wrapped up between a zone capture and its continuation (#214). Go on as for `implement #N`, with `<start>` the sha it names, not HEAD, and in Launch add `--continue <start>`, as Zone capture's step 5 does (`zone-capture.md`), so the worker builds on those commits, and its push and record cover them. `push then implement #N` means the step is `/implement #N`, and the only thing in its way is unpushed commits on the default branch that no run accounts for, such as hand commits (#223): push them first, on approval, before any launch. Read `${CLAUDE_SKILL_DIR}/push-on-approval.md` and run its steps 2 to 5 over `origin/<default>..HEAD`, its checked-push rule included, skipping step 1, since no worker runs yet, and every `close.sh` step, since no worker waits on a close: pass `--id pre-launch` and `--start` the upstream's commit (`git -C "<project folder>" rev-parse '@{u}'`), and with a Distribution repo `--dist-start` its HEAD (the snapshot's `dist head` line, so take the snapshot below first). Capture this session before the question (Capturing this session, below). When the push lands (its `pushed` line), run this step again: it now prints `implement #N`. On a no, no answer, a `fail` line or an error, launch nothing: report the unpushed commits and the reason, and end here. `stop: ...` means any other step, including work in flight in git, or a folder in a linked git worktree (Policy, above): report the line and end here.

Then read the ticket's title and its latest Agent Brief, the comment `/triage` posts, or its body when it has none (`gh issue view N --json title,body,comments --jq '{title, brief: (([.comments[] | select(.body | test("(?m)^## Agent Brief"))] | last | .body) // .body)}'`, run in the folder). The launch summary is the only use of this read, and the worker reads the whole ticket itself; the whole ticket cost a supervisor 3.2k tokens on a ticket with two comments and 11.6k on one with fourteen, this read 1.1k to 1.3k (#228). Record where the branch starts, for the report, and the repo's worktrees and branches, for `watch.sh`:

```sh
git -C "<project folder>" rev-parse HEAD
sh "${CLAUDE_SKILL_DIR}/scripts/watch.sh" --dir "<project folder>" --snapshot > "<scratchpad>/snapshot.txt" </dev/null
```

The first is `<start>`, except after `continue #N from <sha>`, where `<start>` is that sha. With a Distribution repo, the snapshot's `dist head <sha>` line is `<dist start>`, which Push on approval passes as `--dist-start`, and so does every run record (Finishing), so it counts that repo's commits (#216).

## 2. Launch

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/launch.sh" --dir "<project folder>" --ticket N </dev/null
```

Add `--model <id>` when the user gave one; the default is `claude-sonnet-5`, and a model without auto mode (Haiku) is refused. Add `--effort <level>` (`low`, `medium`, `high`, `xhigh` or `max`) when the user gave one; without it the worker runs at the model's default effort. It sets `CLAUDE_CONFIG_DIR` to this profile for the worker, launches in auto mode with `--disallowedTools EnterWorktree,Artifact,Workflow,ScheduleWakeup,SendFeedback`, `--no-chrome`, `--settings '{"worktree":{"bgIsolation":"none"}}'` and the grants text in `--append-system-prompt`, which carries a line telling the worker to read each file once (in ranges, one file per call, never printed again unless changed; 115 tokens, #134), names the worker `worker <project> #N: <ticket title>` with `--name` (cut to 80 characters), so `claude agents` and the Claude app tell workers apart (#103), and reads the job's `state.json` to confirm the worker got this profile, the folder itself rather than a worktree, auto mode, the `EnterWorktree` deny, the setting, the grants text, the effort, the unused-tools deny, `--no-chrome` and any profile excludes. Beyond `EnterWorktree`, the deny list and `--no-chrome` drop tools a worker never uses (publishing a page, workflows, `/loop` wakeups, feedback drafts, the user's browser), which took 19.5k tokens of its context before its first step (#130, `docs/research/worker-fixed-load.md`). When the profile holds `mp-supervise-worker-excludes` (one path or glob per line, relative to `$CLAUDE_CONFIG_DIR` unless absolute or starting `~/`; blank lines and `#` comments skipped), its paths join the setting as `claudeMdExcludes`, so the worker loads without the profile instructions it lists, such as rules that govern only an attended or supervising session (#133); the maintainer writes the file, since it names the profile's private files. The launch confirms them in the job's flags, and a `note:` line on stderr says how many paths it left out and names any literal path that does not exist; report those lines. Without the file the setting is unchanged. The name survives the session-title hook at startup and a `resume.sh` wake; a `/clear` in the worker, which runs that hook again, is untested. When `gh issue view` cannot read the title, the name leaves it out and a `note:` line on stderr says so; report that line. The name is a label, not a check: a job that records another name, or none, keeps running, and a `note:` line on stderr names the name it recorded; report that line. A grant committed but not on origin is left out, and `grant.sh` names it on stderr as `note: ... ignored`; report that line. Without the setting, Claude Code 2.1.286 refuses a background worker's edits in the folder until it isolates, and a worker denied `EnterWorktree` makes its own worktree with `git worktree add` (#83). First it checks the Project is in its main checkout, not a linked worktree, on its default branch, with a clean tree and no other live background session in it, and refuses otherwise: report the error, since a dirty tree or a branch is the maintainer's to settle. Then it checks the Project's setup files (#140) and reports each on a `setup:` line on stderr, before anything launches and before any refusal; report those lines. `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md`, read at the repo's top, must both be there: when either is missing the launch is refused (exit 1), and the error names the missing file and `/setup-matt-pocock-skills`, which writes them. `docs/agents/supervision.md` is read where grants are, on origin's default branch: when it is missing there, the launch goes on and its line says every shared action will wait for approval and names `/setup-mp-ported-skills`, which offers it; a copy committed here but not on origin is reported as not yet in force. Both commands are user-invoked, so give each to the maintainer as a command to type. Once the worker passes its checks it writes the worker's id to the checkout's marker (`git rev-parse --git-path mp-supervise-worker`), which holds this session read-only there. When the Project names a Distribution repo (Policy, above), `launch.sh` also refuses it missing, not a git checkout, the Project's own repo, in a linked worktree, dirty, off its default branch, or with another live background session in it, each error naming it as `Distribution repo <path>`; tells the worker its path in the `--append-system-prompt`; launches with `--add-dir <path>` and confirms the job recorded it; and writes the marker in both repos, the Project's naming the Distribution repo on a `distribution <path>` line and the other naming the Project on a `project <path>` line, so `release.sh` on the Project folder clears both (it prints `released ID in <path>` for the second). A `distribution-repo.md` not on origin is ignored with a `note: ... ignored` line on stderr; report that line. It prints the worker's short id. Exit 1: nothing launched, report the error. Exit 2: the worker failed a check and was stopped, report the error with the id.

With `--watch tmux` or `--watch iterm`, open the worker's viewer now: read `${CLAUDE_SKILL_DIR}/watching.md` and follow it.

Once the launch has succeeded and any viewer is open, and before the watch, tell the maintainer which ticket the worker took, as `#N <title>`, with the worker's short id, and give a few lines on what it asks for: what to build and its acceptance criteria in brief. Build the summary from step 1's read, the latest Agent Brief or the body: no new tracker call. A launch that exits 1 or 2 gets no summary. With `--loop`, each ticket's launch gets its own (#117).

## 3. Watch

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/watch.sh" --id ID --dir "<project folder>" --since "<scratchpad>/snapshot.txt" --zone --detail "<scratchpad>/watch-ID.txt" </dev/null
```

Run it with the Bash tool's `run_in_background`, since a ticket outlasts a foreground call, and wait for its completion notice. It polls `claude agents --json --all` every 30 seconds while the worker is `working`, and returns at the first other state, with the worker's `cwd` on the next line and, for a blocked worker, a `needs` line naming what it waits for. It reads the worker's transcript as well as the list, so a turn that ended returns `done` even while the list says working or blocked, and a turn that ended on a `Waiting on:` line returns `blocked input needed` with that action as the `needs` line (#88, #97, #114). A turn that ended on a `Parked:` line returns `parked`, with the worker's question on a `question` line (#158). A worker that left the Project folder, or made a worktree or branch in its repo (or its Distribution repo) since the snapshot, returns as `moved`, listed in `worktree`, `branch` and `commit` lines. Those lines count every worktree and branch made since the launch, the worker's or another session's, so say so when reporting them. An `other <path>` line is a worktree the Claude app made for its own session, not the worker's: report it as another session's and do not stop the worker for it. A `note` line names a source not read or a reading made from the transcript. A working worker whose transcript has not grown in 30 minutes returns as `hang`; after 4 hours it exits 124 with the last state. When and why each state and line is returned is in `watch.sh`'s header; read it only when a result does not fit the report below. Pass `--zone` on every watch of a worker's build, after a launch or a routine answer, and never on a capture's watch: it returns `capture-due` with a `reading N% of zone` line and a `due` line once the worker's context is due for a capture (#60). Before its first poll, `--zone` works out the worker's auto-compact point from the model the job's flags name; when the force point plus the poll margin reaches it, the watch exits 1 naming both points, reported under Any other state, below (#181). A `note:` line there says the model's window is not known and was read as 200k; report it. A watch that follows `resume.sh` passes `--after <epoch>` from its `after` line (Follow-ups, below), so the turn that ended before the resume is not read as the resumed one's end (#122). A watch after the maintainer answers a blocked worker in `claude attach` adds `--wait-blocked`, which waits through a block while the worker's transcript grows and returns one still waiting, with how long it has waited (`report-states.md`, #87).

`--detail` writes the full result and the worker's whole last message to that file and cuts what the watch prints to a verdict, ending on a `detail <path>` line (#192). A settled `done` (commits since the snapshot, no background command or agent still running, a last message that is no question) prints only the state, `cwd` and any `other` or `note` line besides `note claude agents ...`. Any other `done` adds an `unsettled: <reason>` line and the last message, after a `message:` line, cut to 3000 characters. Every other state prints the lines the Report step needs, and a `blocked question` with no `needs` line also prints the message. `--capture`, on a capture's watch, prints the message in every state. Read the detail file only when the printed lines do not settle the report, such as a message cut short.

## 4. Report

One report, by the first line `watch.sh` printed. A report that ends this session while a zone-captured ticket still has work to build and no continuation launched, on any path, first runs Zone capture's Wrap-up before a continuation: read `${CLAUDE_SKILL_DIR}/zone-capture.md` and follow that section. A `blocked question` or `blocked input needed` first goes through Routine answers: read `${CLAUDE_SKILL_DIR}/routine-answers.md` and follow it; only one it does not answer is reported by the items here. Whatever the outcome, it lists the shared actions the worker took, with `<cwd>` from `watch.sh` and `<start>` from step 1. For a settled run, take them after the capture and any push (Capture, below), since the capture can take shared actions of its own:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/actions.sh" --id ID --dir "<cwd>" --start <start> </dev/null
```

It prints one line for each PR or issue in the worker's job, each remote branch holding its commits, and each push, PR or issue command in its transcript or a subagent's, with whether it `succeeded`, was `refused`, `failed` or has `no result`. A command counts when the #66 hook would refuse it, when it runs a `gh pr` or `gh issue` subcommand that is not read-only, or when Claude Code recorded a push or PR on its result. It prints `none` only when it found nothing and read every source. A branch or command line is marked `granted (<citation>)` when a standing grant in `docs/agents/supervision.md` covers it, read only from the default branch as committed on origin (#58); otherwise `ungranted`. A branch line reads `pushed by the supervisor on the maintainer's approval` instead when `push.sh` pushed it for this worker (Push on approval, `push-on-approval.md`), or `pushed by the supervisor under checked-push (<citation>)`, with the range and the check lines, when it was a checked push. An `issue-comment` or `issue-create` line `posted by the supervisor on the maintainer's approval` is a post `post.sh` made for this worker (Post on approval, `post-on-approval.md`). It reads `pushed by someone else`, neither granted nor ungranted, when no call in the worker's transcripts that succeeded or has no result pushed to it, such as a branch the maintainer pushed from their own terminal; a refused or failed push of the worker's does not count (#98). When a transcript could not be read, the branch is read as the worker's. Report a `granted` line too -- it is what the maintainer's standing grant already approved, not something to re-approve -- report every `ungranted` line as a shared action the maintainer did not approve, a `pushed by someone else` line as no action of the worker's, and every `note` line as a source that was not read, never as no actions.

- **`done`**: the ticket and its commits, `git -C <cwd> log --oneline <start>..HEAD`, the shared actions, and whether the ticket is closed (`gh issue view N --json state`). `done` means only that the worker's turn ended: an unsettled `done` prints the worker's last message after its `unsettled:` line; with no commits and the ticket open, read that message, since the worker may have ended on a question asked in plain text, and report that as blocked with `claude attach ID`. A background command still running is reported with the message too, the worker left running. Otherwise the work is settled: send the capture first (Capture, below), unless this `done` is the capture's own. Then end the run with `finish.sh` (Finishing, below), which stops the worker, still live, and does the rest of this report's closing steps. When `cwd` is not the Project folder, say the commits sit in that checkout, on a branch nobody pushes, and send no capture: the worker is out of its folder, as for `moved`.
- **`capture-due`**: the worker's context passed its capture threshold mid-ticket: read `${CLAUDE_SKILL_DIR}/zone-capture.md` and follow it instead of the rest of this step.
- **`parked`**: the worker parked its ticket on a decision only the maintainer can make (#158): its `question` line, posted on the ticket as a comment opening `## Parked`, and its work on the local branch `parked-N`, `git -C "<project folder>" log --oneline <start>..parked-N`, with the Project's branch reset to `<start>`. The work is settled as it stands, and the worker ran its own capture before posting the park comment (`launch.sh`'s park line), so the question stays the ticket's newest comment: send no capture, and end the run with `finish.sh` (Finishing, below), whose run record lists the question and the branch and which `state.sh` does not count as a reply. `state.sh` passes over the ticket until someone replies after the park comment, so the next ticket is not this one. A `Parked:` line comes only from a worker `launch.sh` told to park, one with both the `issue-comment` and `sub-issue` grants.
- **`blocked input needed`** whose `needs` line is a `git push` no grant covers: the work is settled. Send the capture first (Capture, below), unless this block is the capture's own, then read `${CLAUDE_SKILL_DIR}/push-on-approval.md` and follow it instead of the rest of this item. Do not tell the maintainer to push from a terminal, with a `!` command, or by telling the worker: the first two do not work from a remote client, and the hook refuses the third.
- **`blocked input needed`** whose `needs` line relabels the worker's own ticket to `ready-for-human` (`gh issue edit N` adding that label, with or without removing `ready-for-agent`), when the block is the build's, not the capture's, and `git -C "<project folder>" status -sb` shows the branch even with its upstream (with a Distribution repo, that repo's too, `git -C "<distribution repo>" status -sb`): the work is pushed and settled, and the relabel waits only on a live check no grant covers (#204). Send the capture (Capture, below), and ask the maintainer nothing first: its live-check step runs `live-check.sh`, which takes the relabel and the move after the parent's last open `ready-for-agent` child together, and ends on `Waiting on: ... live-check.sh --apply N`, which Capture's step 3 puts to the maintainer as one question. When the capture then returns `done` with the ticket still labelled `ready-for-agent` (`gh issue view N --json labels`), its live check did not run: before `finish.sh`, take Capture's step 3 `live-check.sh` bullet for #N, so a shipped ticket is not built again. A branch ahead of its upstream, or a relabel of another ticket or to another label, is reported as the other states are.
- **`blocked input needed`** whose `needs` line is a `gh issue comment` or `gh issue create` no grant covers, when the block is the capture's own (Capture, below): the work is settled. Read `${CLAUDE_SKILL_DIR}/post-on-approval.md` and follow it, after Push on approval when a push also waits (Capture's step 3), instead of the rest of this item. The same block before a capture, from the build, is reported as the other states are.
- **Any other state** (`moved`; `blocked permission prompt`, `blocked input needed` or `blocked question` that none of the above takes; `hang`; `stopped`; `gone`; `unknown ...`; exit 124 or 1): read `${CLAUDE_SKILL_DIR}/report-states.md` and report it as that file says.

### Finishing

A settled run (`done` after its capture and any push, the end of Push on approval or Post on approval, and Zone capture's step 4) ends with one call, run in the Project folder, with `<cwd>` from `watch.sh` and `<start>` from step 1. With a Distribution repo, add `--dist-start <dist start>` from step 1; without it, the record says that repo's commits were not counted. Add `--tmux` with `--watch tmux`, or `--pane '<session> <window> <tab>'` with `--watch iterm`, unless the viewer is already closed:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/finish.sh" --dir "<project folder>" --cwd "<cwd>" --id ID --start <start> --ticket N --record "<scratchpad>/run-record.md" --session "${CLAUDE_SESSION_ID}" --session-dir "$PWD" </dev/null
```

With a Distribution repo:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/finish.sh" --dir "<project folder>" --cwd "<cwd>" --id ID --start <start> --dist-start <dist start> --ticket N --record "<scratchpad>/run-record.md" --session "${CLAUDE_SESSION_ID}" --session-dir "$PWD" </dev/null
```

It runs, in order, `stop.sh`, `view.sh --close`, `actions.sh`, the glance, `record.sh` to the record file and `gh issue comment` posting it, each as the passages below describe, and writes their full output to the `detail` file it names. When nothing needs the maintainer it prints one `clean <url>; shared actions: ...; glance: <reading>` line: report the URL as the run record's comment, the shared actions (`none`, or the ones the record lists), and the glance line as it reads. Otherwise it prints one line per item, each reported as the passages below say: an `ungranted`, `pushed by someone else` or `note` line from `actions.sh`, `viewer not closed:`, `actions not read:`, `record failed:`, or `post failed: ...` or `post printed no URL` with the record's path; then `record <url>`, the shared-actions count and `glance:`. Read the detail file only for an item whose line does not say enough. A `stop failed:` line, with the `finish with:` line after it, exits 1 before anything past the stop, and a refusal of the `finish.sh` call itself, by the classifier or a permission prompt, runs none of it: for either, read `${CLAUDE_SKILL_DIR}/stop-refused.md` and follow it. On a worker that Push on approval or Post on approval already stopped, `stop.sh` finds it stopped and the rest runs as usual.

The passages below are for what `finish.sh` does not cover: `moved`, `stopped`, `gone`, and a worker left running.

### Stopping

Stop a live worker the policy says to stop (`moved`, and step 1 of Push on approval and Post on approval; after `done`, through `finish.sh`) with `stop.sh`, never a bare `claude stop ID`, and pass the Project folder, not the worker's `<cwd>`, since the folder's repo holds the marker even when the worker has moved:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/stop.sh" --dir "<project folder>" --id ID </dev/null
```

A bare `claude stop` of the supervisor's own finished worker was refused by the auto-mode classifier as interfering with a running job (#132), so the stop goes through `stop.sh`, not a permission allow rule, which would allow every `claude stop` from this profile and is a settings edit only the maintainer can make. `stop.sh` checks before stopping anything that the job is in this profile's `jobs/` and the folder's marker names it or is gone. It waits until `claude agents` shows the worker stopped or gone, or has shown no pid for 60 seconds (`--settle`), so its cost row is written before `record.sh` reads it, then releases its marker. It prints `stopped ID` (or `gone ID`), then `released ID` or `no marker in <folder>`. Exit 1, in two kinds: a check failed first and nothing was stopped, which the error says; or the worker was not seen to stop, or was stopped and its marker not released, and the error says whether the checkout is still read-only and ends on a `finish with:` line, the command that finishes the run.

When the stop is refused, by the classifier or a permission prompt, or `stop.sh` exits 1 with a `finish with:` line, read `${CLAUDE_SKILL_DIR}/stop-refused.md` and follow it: do not route around the refusal, and do not stop mid-report.

To read a worker's last output, print its last message from its transcript, which `last-message.sh` finds by the job's `sessionId` in any project folder, since a worker that entered a worktree has its transcript moved:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/last-message.sh" --id ID </dev/null
```

`--count N` prints its last N messages, oldest first. A `note:` line says when the message may not be the worker's last word: its turn ended with background agents pending, whose reports start another turn, so the message is often an interim "waiting for agents" note; or its turn has not ended. Report it as such, not as the worker's summary. Exit 1, with nothing printed but an `Error:` line, means no message was read (no such worker, no transcript, or none written yet); report that, never an empty output as the worker's.

Not `claude logs ID`: it prints the worker's raw terminal stream, cursor moves and colour codes included, which reads as noise (`[42B[38;2;215;119;87m✻`) rather than as the worker's words.

Release the marker whenever the worker was stopped or is gone, and `stop.sh` did not already, so the checkout is writable again and the next launch finds no stale mark (a stale one does not block `launch.sh`, but it keeps the hook refusing):

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/release.sh" --dir "<project folder>" --id ID </dev/null
```

It prints `released ID`, or `no marker in <folder>`, then `released ID in <path>` when it also cleared the marker in the Project's Distribution repo. Exit 1: the marker names another worker, or the folder is not a checkout; report it and leave the marker.

With `--watch tmux` or `--watch iterm`, once the worker is stopped or gone, close its viewer: read `${CLAUDE_SKILL_DIR}/watching.md`, Closing the viewer. While the worker is left running (`blocked`, `hang`), leave its viewer open, in either mode: it is where the maintainer answers.

At each worker's report, whatever the outcome, run the glance (for a settled run, `finish.sh` runs it, after the capture and any push) for this supervisor session and put the line it prints in that worker's report. It is how a maintainer on a remote client, with no status line, sees the supervisor approach its zone, which with `--loop` stops the loop (Zone stop, `loop.md`):

```sh
sh "${CLAUDE_SKILL_DIR}/../glance/scripts/glance.sh" "$PWD" "${CLAUDE_SESSION_ID}" </dev/null
```

Pass this session's own folder, `$PWD`, not the Project folder: the reading is kept under the folder the session started in, matched exactly, so from the Hub the Project folder finds none. It prints this session's reading (`63% of zone`), or one line naming why there is none (`No reading: ...`, `No reading yet: ...`). For a session with no reading, report that line as it reads, never a number in its place.

Then record the run, whatever the outcome, with the same `<cwd>` and `<start>` and the ticket's number, and with a Distribution repo `--project "<project folder>" --dist-start <dist start>` as well. For a settled run, `finish.sh` records and posts it after the capture and any push, once the worker is stopped, so its `captures and clears` field counts the capture and its shared actions show the push:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/record.sh" --id ID --dir "<cwd>" --start <start> --ticket N > "<scratchpad>/run-record.md" </dev/null
```

With a Distribution repo:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/record.sh" --id ID --dir "<cwd>" --project "<project folder>" --start <start> --dist-start <dist start> --ticket N > "<scratchpad>/run-record.md" </dev/null
```

It prints the record as a Markdown list, one field a line; `record.sh`'s header names each field and where it comes from. `supervisor context` is this session's context at its last call before the launch and at its last call so far, as a percentage of the zone: what the run cost a loop's zone (#118). A field whose source was not read says `unknown`, with a `note` line naming the source. The supervisor's own cost reads `unknown` while this session runs, because a running interactive session's transcript holds no cost row yet; its calls and tokens are still counted. Post it on the ticket, run in the Project folder, and include it in the report:

```sh
gh issue comment N --body-file "<scratchpad>/run-record.md"
```

`record.sh --session <session id>` in place of `--id` records a plain interactive session, such as a hand-run `/implement` of a ticket the same size, leaving out the job's fields: that is the baseline a supervised run is compared against.

### Capturing this session

Claude Code can auto-compact a session that has sat idle, and a supervisor spends most of a run idle: in a worker's background watch, and in a question that can wait for hours. A compaction then drops whatever this session learned since it last captured: in the #185 run the supervisor captured once, at 93% of zone, after two long watches and two open questions (#205). So run `/mp-ported-skills:capturing` in this session, not the worker's, whenever anything is new since this session's last capture, at each of these points:

1. **After each worker's report**, whether `finish.sh` printed it or another state produced it, and before the next launch, resume or watch, a zone capture's continuation launch included. In a single-ticket run this is the run's last capture.
2. **Before a question to the maintainer** that ends this session's turn, such as Push on approval's or a live check's, so the wait for an answer is not a pause with nothing written down.

Each capture covers only what changed since the last one, so a loop's captures stay short. The capture after a loop's final report stays (Zone stop, `loop.md`).

## Capture

A worker whose work is settled ends with `/mp-ported-skills:capturing` in its own session, before any push and before it is stopped for good: only that session holds what it decided and learned. A peaked zone, a long ticket, or a context near or past compaction is no reason to skip it or move it to a fresh session.

- **When:** as soon as the work is settled, before any push: after `done` with the work committed, after `blocked input needed` whose `needs` line is a `git push` no grant covers, and after `blocked input needed` whose `needs` line is the post-push `ready-for-human` relabel of the worker's own ticket (Report step).
- **Not** after `parked`, whose worker captured before its park comment (Report step), nor after `moved`, `hang`, any other block, `stopped` or `gone`, nor after `done` with `cwd` outside the Project folder: a worker left running is the maintainer's to answer, and one out of its folder is stopped as it stands.

Capturing after the push cost a second round of Push on approval each time the capture committed (#67, #98), and its report then described push state from before the push. So the capture goes first, and one push covers the work and the capture's commits.

- **A worker whose own grant covers its push** pushes as soon as the grant's conditions hold, in its build turn, and the capture comes after that push: a capture that commits pushes a second time. `launch.sh`'s grants text tells it so, and that the capture's commits go under the same grant only when the grant's note names a capture's commits (`its capture's commits included`); otherwise the capture ends on `Waiting on: git push`, and Push on approval pushes them (step 3). The other order, the worker capturing before its granted push, was not chosen (#131): it would move the capture into the build turn, before the ticket's close and any other granted action that follows the push, so the capture would describe the work as unpushed and open, and the supervisor would have to find that capture in the transcript to skip its own. A second push under a grant needs no approval round, so it costs only a push; workers read a note silent on the capture's commits both ways (#155 held its commit for approval, #144 and #138 pushed theirs), which is why the grants text names the case. Report the capture's push among the shared actions.

1. Take a fresh snapshot, since the worker's first watch is over:

   ```sh
   sh "${CLAUDE_SKILL_DIR}/scripts/watch.sh" --dir "<project folder>" --snapshot > "<scratchpad>/snapshot-capture.txt" </dev/null
   ```

2. Send the capture as a follow-up (Follow-ups, below), and with `--watch tmux` or `--watch iterm` open the viewer again once it prints `resumed ID` (read `${CLAUDE_SKILL_DIR}/watching.md`):

   ```sh
   sh "${CLAUDE_SKILL_DIR}/scripts/resume.sh" --id ID --dir "<project folder>" --prompt "/mp-ported-skills:capturing" </dev/null
   ```

3. Watch it as in Watch (section 3), with `--since "<scratchpad>/snapshot-capture.txt"`, `--after <epoch>` from the `after` line `resume.sh` printed, `--capture` in place of `--zone`, and `--detail "<scratchpad>/watch-capture-ID.txt"`, so it prints the capture's last message, its report, in every state; and go on by its first line:
   - **`done`**, with nothing waiting on a push: the Report step for `done`, with no second capture.
   - **`blocked input needed`** on a `git push` no grant covers: the capture committed, or the work was already waiting on the push. When the capture's message names `live-check.sh --apply N` as well, on the same `Waiting on:` line or another, take the `live-check.sh` bullet below instead: the `needs` line holds only the last `Waiting on:` line, and this bullet alone would drop the relabel.    - **`blocked input needed`** on a `gh issue comment` or `gh issue create` no grant covers: the capture found something it could not post. When the capture's message names `live-check.sh --apply N` as well, take the `live-check.sh` bullet below instead, which posts after the live check: the `needs` line holds only the last `Waiting on:` line. Otherwise, when a `git push` also waits (its report lists one, or `git -C "<project folder>" status -sb` shows the branch ahead), Push on approval first (read `${CLAUDE_SKILL_DIR}/push-on-approval.md` and follow it); then Post on approval: read `${CLAUDE_SKILL_DIR}/post-on-approval.md` and follow it.

When a `git push` also waits (the capture's message names one, or `git -C "<project folder>" status -sb` shows the branch ahead, or with a Distribution repo `git -C "<distribution repo>" status -sb` shows that one ahead), Push on approval first, up to its step 6, so the live check is asked before `finish.sh` stops the run (read `${CLAUDE_SKILL_DIR}/push-on-approval.md` and follow it). ## Follow-ups

No command sends input to a running background session, so a follow-up to a worker, such as the capture (Capture, above), goes by stop and resume:

```sh
sh "${CLAUDE_SKILL_DIR}/scripts/resume.sh" --id ID --dir "<project folder>" --prompt "<prompt>" </dev/null
```

It stops the worker, waits until `claude agents` shows it `stopped` or has shown no pid for 60 seconds (`--settle`), then until the daemon's roster (`$CLAUDE_CONFIG_DIR/daemon/roster.json`) no longer lists the job, since a resume while the daemon still holds it starts a copy (#185; past `--timeout` it resumes anyway, and the retry below catches a copy), and resumes the job's original session id with the prompt and no flags. It refuses while another background session is live in the same checkout, naming each. A resume that starts a copy instead of waking the worker loses the launch's EnterWorktree deny, auto mode and model, so the copy is stopped and removed at once, the worker stopped again, and the resume retried, up to 3 times (`--tries`). It prints one line for each copy, then `after <epoch>` and `resumed ID`; name every copy in the report. On a wake it writes the worker's marker again, since the worker is live again, and prints a `note` line first when it could not; report that line. Release the marker again once the follow-up's worker is stopped. The id stays the same, so watch it again with `watch.sh`, adding `--after <epoch>` from the `after` line. Right after the resume, the worker's transcript still ends on the turn that ended before the stop, and a watch without `--after` reads that as the follow-up's turn ending and returns `done` while the follow-up still runs (#122). With it, only a turn end written at or after that time counts. Then, with `--watch tmux` or `--watch iterm` open its viewer again once `resumed ID` is printed, never before: read `${CLAUDE_SKILL_DIR}/watching.md` and follow it. Exit 1: nothing resumed, report the error. Exit 2: every try started a copy; each was removed, the worker is left stopped, and the error names them all.

Done when the report names the ticket (with `--loop`, each ticket the loop ran, and the condition that ended it), the outcome, each zone capture with its reading and the continuing worker's id, each question the supervisor answered with its answer, the shared actions (or `none`), each post on approval with its URL or the finding as unposted, either its commits or the id with `claude attach`, the capture's report for a settled run, the run record's comment, and this session's capture after each worker's report and before each question that ended its turn; and for a loop's `zone` stop, the loop summary's URL, the actions waiting on the maintainer, and this session's own capture after the report.
